- More

### Premium entitlement safety

- `PremiumAccess` is the central customer entitlement boundary.
- raw `PremiumEntitlementStore` checks are prohibited outside `PremiumAccess` by CI.
- developer Premium simulation defaults OFF and is owner-only.
- remote Premium disable/maintenance/min-version overrides entitlement.
- expired Premium returns Free.
- Member Dossier and Faction Pulse self-gate as defense-in-depth.
- automatic monetization fails closed while `MONETIZATION_APPROVED=false`.

### Permission freshness

Leadership-only Android routes no longer rely on a 10-minute cached faction position when access is being decided.

- `TornApiClient.authenticateFreshFaction()` evicts cached faction identity, faction alias, position abilities and the cached AuthSession before re-authentication.
- Activity Tracker, Faction Pulse, Member Dossier and WarPay navigation use this fresh path every time they are opened.
- leadership authorization is evaluated before Premium authorization, so Premium can never create faction authority.
- ordinary member navigation keeps normal caching, avoiding unnecessary Torn traffic.
- `tornfca-permission-freshness-audit.yml` protects this boundary.
- shared Faction, Community and WarPay backends independently re-check current Torn faction scope where authorization depends on it.

### Shared backend hardening

Audited source versions:
- Faction backend `1.1.0`
- Community backend `1.6.0`
- Premium backend `1.2.0`
- Developer backend `1.3.0`
- WarPay backend `1.1.0`

Shared-service protections include:
- current faction scope/position refresh where tenant authorization depends on it
- faction-scoped shared records
- no client Torn API-key persistence
- ScriptLock around duplicate/concurrent-sensitive upserts
- Premium payment receipt idempotency
- WarPay cloud upsert serialization
- conservative Community moderation defaults
- aggregate Developer user counts without API key/name telemetry

Community v1.6 scale hardening additionally keeps the chat hot path bounded: active chat polling reads recent 500-row chunks and stops once it has enough messages or reaches a 5,000-row scan ceiling, rather than loading the entire historical ChatMessages sheet on every poll. Exact message/report lookups use row finding instead of whole-history reads. This improves growth behavior but is not a substitute for deployed load testing.

## Pending product-policy decision that does not block technical integration

### Community moderator capability matrix

The backend is ready for capability-based moderator authorization, but the final list of qualifying Torn abilities is intentionally not invented. Owner-only recovery/global moderation remains the safe default until the policy is chosen.

### Real Premium sales

See `docs/MONETIZATION_RELEASE_GATE.md`.

The app/backend architecture can reach v1.0 technical readiness with automatic Premium payment processing OFF. Real paid activation has an additional Torn/distribution-payment approval gate and should not be used to rush the technical release.

## v1.0.0 promotion criteria

Do not rename/promote to v1.0.0 until all of these are true:

- all five backends live at the audited versions
- live-backend audit passes
- Premium Matrix/source/permission-freshness audits pass on the candidate
- permanently signed Beta is produced and signature/package verified
- device smoke/matrix passes, including Beta/production command-shell parity, branding separation, permission-change checks and Community growth checks
- no critical cross-faction, entitlement, stale-permission, payment-replay, command-shell or offline-state defect remains
- legal/data-use disclosure is accepted and tested
- explicit approval is given to promote the tested candidate

At that point, create a final restore point, move the tested source to `1.0.0`, rebuild/sign, repeat the release smoke test, and only then consider promotion to `main`.
